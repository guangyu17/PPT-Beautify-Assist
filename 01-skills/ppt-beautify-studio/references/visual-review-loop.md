# 真实渲染、visualize 复核与自主修复闭环

所有模式必读；先遵守 [载荷控制](payload-budget.md)，其临时IFAPI完整body门禁优先；原生默认无该门禁。目标是“当前实际渲染暂未发现明显问题”，不是宣称完美，也不是把修复留给用户。
有动画、3D或视频时另按 [动态播放检查](motion-3d-ppt.md) 核验最终PPTX在目标宿主的放映；本页静态渲染通过不能代替时序、交互或媒体验证。
复用 `compose_slide.py`、`render_preview.py`、`check_layout.py` 和 visualize，不再造 PPT 渲染器或
假视觉打分器。visualize 是展示与对照界面，视觉判断由主代理实际查看渲染图完成。

## 1. 触发时机与证据

- 每张 IF API 资产返回后先检查该资产；回填成完整页面后必须再看实际 PPTX 的整页效果。
  单独无字背景合格不等于“背景＋边框＋真实文字”的组合合格。
- 每套风格样张展示前、每个已完成生产批次、每个修改版本、最终导出，都执行本闭环。
  新完成页/被修改页逐页查看；模板、字体、底色或共享装饰改变时，所有受影响页面都重新渲染复查。
- 已检查且依赖未变的页可保留记录，不能用“抽查封面没问题”代替整套检查。最终交付重新渲染
  最终 PPTX 全部页面，拼图看一致性，逐页看细节，防止局部样张与最终导出不同。
- 每轮存到 `previews/review-r01/`、`review-r02/` 等新目录，保留真实 PNG、渲染报告和对应版本 PPTX。
  保留修复前后图，不覆盖原件。截图或 CSS 后处理不能冒充修复后的 PPTX 渲染。

## 2. 用 visualize 组织真实复核图

创建/更新视图前完整读取宿主给出的 visualize SKILL.md；上下文压缩后重新读取。
当前依赖由技能列表中的 `$visualize:visualize` 路径提供，不把此机器的插件版本路径硬编码到包内。

- 视图只用 Office 导出的真实 PNG（可做缩略图），不重画文字、不伪造版式。
  优先显示本轮修改页；有修复时并排“修复前／修复后”，再显示问题部位裁切图（来自同一真实 PNG）。
- 视图中保留必要页号、版本和问题标签，例如“边框净空”“正文对比度”；不要塞长篇自检报告。
  单幅缩略图不足以判断文字贴边，必须从原始渲染提取可读的局部裁切检查；全局还须看页面整体平衡。
- 主代理用可用看图工具（当前 `view_image`）实际查看由每页真实 PNG 生成的按可读性与实际请求大小选择的检查副本和必要原图局部裁切；如果有浏览器
  检查能力，再查看渲染后的视图以确认图片/切页正常。没有浏览器能力时不要声称运行验证过界面。
- 遵守visualize自身的HTML fragment/资源/可读性要求，但撤销本技能256KiB视图与固定小图限制。
  不无谓打印大段Base64；使用实际支持的资源方式，不能猜不存在的attachment URL。视图太大按实际需求分开呈现。
- 内部每轮实际看图，选择/需要对照/交付时更新当前视图；不强制“4次图像就结束”。
  IFAPI桌面发送前必须测最终body，native不加该临时限制；任何出现的真实超限按其链路处理。
  风格门仍等待用户，普通局部修复不额外审批。无法展示visualize就说明并显示可用的真实图，不谎称看过。
- visualize 不可用或图片没有实际显示时，报告该限制并用真实PNG的受限检查副本/必要局部完成直接看图；可以继续已授权
  的局部修复，但不能将未显示的视图记录为通过。无法查看真实图像时，不得宣称视觉验收完成。

## 3. 每页检查清单

| 项目 | 看什么 | 明显问题的例子 |
|---|---|---|
| 边框与内容净空 | 可见花纹的内缘/开口，不只是图片矩形 bbox | 框太小、正文贴框、角饰压住字、框线从正文背后穿过 |
| 层叠与透明 | 底色→背景/装饰→内容；透明开口是否真的透明 | 白色假透明盖住内容、框置顶遮字、只把框置底但字后仍有花纹 |
| 背景深浅 | 正文字形与其下方最复杂区域是否可辨 | 深字落在深纹理、浅字落在高光、不同页明暗突变 |
| 纹理与透明度 | 花纹是否抢正文注意力 | 纹理太实、框线太重、减透明后反而与字同亮度 |
| 文字排版 | 字号、行距、段间距、框内边距、对齐 | 截字、挤成一团、末行顶到边、标题与正文抢层级 |
| 图片/图表 | 图片比例、裁切、标注、表格各单元格 | 人像被拉长、图表标签溢出、细线被背景吞掉 |
| 页面完整性 | 边缘、页序、整页留白、原文与对象 | 框放大后被裁断、底部来源丢失、某页风格跳变 |

普通文字与大字对比度要求沿用 [版式规则](layout-typography.md)。检查最不利的实际叠层区域；
`check_layout.py` 的背景采样忽略部分叠层，不能仅凭它的状态放行。

## 4. 修复优先级：先本地调整，再决定是否重新生成

### 边框过小、贴字或在文字正下方

1. 以实际可见内缘确定内容可用区，比较真实文字/图片边界和 `safe_zones`。16:9 正文到内框可先以
   0.15–0.25in 净空作为设计起点，密集花纹留得更宽；这是可调参考，不是统一强制间距。
2. 能修复时扩大内框或等比放大/移动独立边框，使内缘离开正文；单次可先试 5%–10% 小幅调整，
   修正 x/y 使视觉居中。每次检查四周是否出界、角饰是否被裁、图片清晰度是否降低。
3. 只有外框变大、内侧花纹仍压字时，不能继续盲目放大。改内开口/边框样式、减少装饰密度，
   或在不删字的前提下移动正文、重新分栏/增加留白。优先让装饰让位，不能为框而强行缩字。
4. 把装饰放在文字下方只能修正前后顺序，不能消除字背后的杂纹；仍需扩大净空或为文字区
   加干净底板。装饰已与不透明背景合并时，不能独立移动框，需局部编辑/受限重新生成背景。
5. 确需 IF API 修复时，提示词只改缺陷，例如“保留风格，扩大中间无字净空，四周框仍完整”，
   使用原参考与准确 safe_zones；仍计入同一资产的原有重试预算、当前通道与请求预检规则。

### 背景过深、过浅或纹理太强

- 先判断文字应深还是浅，再调背景，而不是一律加黑。保持已确认的色调/品牌色；大幅换色需重新确认。
- 纯色直接改 `background_color`。一张不透明底图盖在上面时，修改底色不会生效，不能假装修好了。
- 优先在背景上、文字下加入轻量深/浅色原生遮罩，或微调已有生图材质底板的alpha；小步调强度、重渲染看结果。不能新增原生平板假冒材质对话框。
  背景遮罩别遮住前景照片。正文前景顺序保持正确，且不能以遮罩把所有装饰涂没来冒充华丽风验收。
- 要降低独立装饰本身的存在感，可调整其 PNG alpha 副本或图像明暗；优先使用 [多层配方](layer-recipes.md) 保存每层角度/节点/gamma/opacity 和相对顺序，允许反复叠加调整但须可回放。只处理背景/装饰，不改原图证据、
  品牌 Logo、数据图形或正文。每个副本保存来源和参数，防止反复叠乘导致不可追溯。
- 减少不透明度可能让底色透出并改变对比，仍须检查整页；不是“透明一点”就自动合格。

### 当前脚本支持的落地方式

- `compose_slide.py` 已支持 `background_color`、图片 `x/y/w/h/fit`、文本 `fill/fill_alpha`、形状 `fill/alpha`。
  `alpha` 与 `fill_alpha` 表示**不透明度**，0 完全透明、1 不透明；30% 透明度对应 alpha=0.7。
- 改装饰大小/位置编辑 layout JSON；改层级调整 `elements` 顺序。半透明遮罩用原生 rect 的 `alpha`，
  不对正文文字本身降低 alpha。全页背景之后、文字之前的形状可用于调深浅。
- 当前脚本**没有**图片 `opacity` 或 `background_opacity` 字段，不能随意写这些字段后声称已生效。
  真正需要改装饰透明度时，用本机现有 Pillow 对原始 RGBA 副本的 alpha 通道乘以目标不透明度，
  保存新 PNG 后更新图片路径；保留原透明区域。只需柔化背景时优先原生遮罩，无需重新调用 IF API。
- 每次修复都重新 compose 实际 PPTX，再运行布局检查与 Office 渲染。只改 visualize 图上的 CSS、
  缩放或透明度不是交付文件修复，不能接受。

### 新增融合与字体检查

有渐隐 PNG/人物抠图时，查看 [图片融合](image-blending.md) 验收项：文字区是否干净，主体是否被淡没，
透明区是否露出正确底色，有无硬边、白边或灰色光晕；抠图和展开不得改变人物身份/事实资料。
渐隐强度、明暗、整体 alpha 优先用 blend_image.py 从原图派生并记录，无需额外 IF API 请求。
有字体改动时，检查标题/正文搭配、实际中英字形、缺字替代、换行、标签/图表的数字；
安装记录或 font 字段不能证明 Office 真用上了目标字体，必须看新渲染。

## 5. 有界自主迭代与验收

模式1视觉重设计/模式3另按 [设计评审与减法](distinctive-design.md) 使用brief评价讲述效果，先做最多两轮审美精修，每轮聚焦1–3项。评审只输入真实渲染、brief与必要参考；允许委派时可独立评审，否则标为自查。模式2不做风格重构。
审美轮次计入每页4轮本地修复；两轮后停止无目标的审美迭代，不豁免溢出、丢字、遮挡等缺陷。缺陷继续受下述上限和停止条件约束。

正常流程是检查发现问题就主动修复，不逐项等用户指示；不得因为首遍脚本成功就直接交付。
一次完整修复＋重新渲染＋重新看图算一轮，默认每个受影响页面最多 **4 轮本地修复**。
IF API 单资产仍是首次调用＋最多 3 次重试的总上限；本地轮次不重置出图预算。

- 每轮先写可观察的问题（页号、对象、区域、现象），一次修复相关问题，再回看是否解决且有无副作用。
  没有具体问题时停止，不能为了凑足轮数无限“优化”；同一问题连续两轮没有改善时暂停该页，说明需要的决定。
- 达到上限仍明显不合理时，保留最好的版本和未解决问题，标记 `needs_attention` 并请用户决定继续修复
  或接受有披露的草稿；不能因为额度耗尽就标记 passed，也不能擅自突破原有 API 重试限制。
- 只有最新 PPTX 实际渲染已逐页查看、原文/页数/顺序核对、已发现问题有复查证据、无新明显遮挡/裁切/
  低对比度/拥挤问题时，才标记 `no_obvious_issues_at_review`。用语是“本轮视觉复核暂未发现明显问题”。
- 对本轮生成或修改的整套，在最终输出前检查完整页序拼图，并检查本轮最终渲染的每页。
  正文、图表/表格及承诺独立的对象仍原生/独立；用户明确批准的一体化视觉背景内的图像对象是已披露的例外。
  修复不能靠把整页含字扁平化，也不能改文案替换事实。
- 模式 2 的目标是原页：修复重建引入的偏移、遮挡、透明度差异；原稿本来拥挤不代表可自动放大框或换背景。
  若忠实还原与美化冲突，保持原稿并说明，询问是否另存美化版本。简约风仍不新增华丽装饰。

## 6. 记录与交付

工作区保存 `logs/visual-review.json`：每次 `revision`、实际 PPTX 与布局/素材的 SHA-256、
`render_report`、逐页 PNG 路径、`visualize_path`、页面检查状态、问题区域、修复动作、前后证据、
本地修复轮次、API 资产/累计调用数、剩余问题及停止原因。记录实际看过什么，不以写日志代替看图。
模式1/3另记 `design_review`：brief版本、self/independent、本轮真实图片、问题区域/影响/动作、实际删减和前后对照。删减不触及受保护的原文、数据与来源；主观美学分数不作为通过依据。
源文件、布局或素材一旦变更，旧检查结果失效，必须重新渲染受影响页；全局变更全套复查。
交付最终PPTX与磁盘上的完整拼图；在对话仅展示受限概览/安全的小型visualize视图，不把完整高清拼图重新上传；有未解决问题先说明，不把待修草稿称为完成版。


## 全套合同与新叠层复核

批次及最终拼图须对照 layouts/deck-style.json：标题位置、字体、色温、背景语言、框线与排版家族一致。
每轮透明度调整都记录具体层、angle、stops、curve、gamma、opacity；多层白雾叠加可能洗白主体，
不能只看单层“透明度都不高”。按 [多层配方](layer-recipes.md) 重建实际文件，保留前后证据。


## v1.6 材质/结构验收

检查灯笼/罗盘等图标是否对应原文、全套统一；环框净空和小尺寸可读性；线的端点/箭头方向、
分支是否有原文依据；时间轴日期/顺序/比例说明；磨砂面板是否出现旧文字重影、取样接缝和过强高光。
线穿字/正文底色不清晰不能只通过重叠豁免放行。参考 [组件设计](semantic-components.md) 和
[组件JSON](component-schema.md) 做可追溯原生修复；全页图仍先做受限检查副本，按413规则保存断点。


## v1.7 材质来源验收

新设计的材质panel必须有真实生图日志与纹理文件，原生形状/模糊补丁不能替代。中低档可以不用，但不能假造。原生安全遮罩只是背景可读性修复，不得改名绕过面板规则。
